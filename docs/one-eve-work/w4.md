## Approach

- Parser `instance?` / `condp instance?` class-name branches (#295–#309, #298–#321, etc.): eve.deftype interned the class but not a var at `dp/BindScalar`, so a qualified `dp/BindScalar` does not compile on the JVM. Local type tokens `(def Variable (type (dp/->Variable nil)))` (and the same for the other AST types) are the class on JVM/CLR, the constructor on cljs/nbb, and bb's stamped `:type` token (`host_completion` rewrites `type`/`instance?` for SciMap). Then every site uses the token with no reader conditional. The `#?(:clj/:cljr)` `:import` of those parser types (plus unused `IReduceInit`/`Counted`/`Datom`) is deleted.
- `#?(:clj (dp/->Constant subs) :cljr (dp/->Constant subs) :cljs (dp/->Constant subs))` already had identical arms; folded to `(dp/->Constant subs)`.
- ArrayRelation / CollRelation print: `IPrintWithWriter` + `eve.core/-write` (the LRU/AutoTempid house style that eve.deftype realizes per host). Shared `pr-rel-str` writes the literal type name, so the `.getSimpleName` / `(str (type rel))` branch goes away. The two `print-method` `#?(:clj/:cljr)` forms are deleted.
- `Math.sqrt` / `js/Math.sqrt` / `Math/Sqrt` in `aggregate-stddev`: folded to a local Newton's-method `sqrt` (clojure.core only).
- SingletonRelation (in this file) only implemented the IRelation methods its call sites used. basilisp requires every protocol method at compile time, which became visible after the print fold removed the `^java.io.Writer` hint that baseline already failed on. Completed `-project`, `-alter-coll`, `-getter`, and `-union` with empty-symbol singleton stubs so the ns loads on basilisp.
- Left `fast-map` / `fast-arr` / `fast-set` (`#290–#292`) untouched (John's design call: java.util collections vs clojure.core, needs a JVM benchmark).
- `storage.cljc` `:lpy` `defprotocol` carve-out kept as glue: basilisp's `defprotocol` cannot take `:extend-via-metadata`.

query-v3/`q` of `[:find ?n :where [?e :name ?n]]` returns `#{[nil]}` on both this tip and unmodified `22ea73167`; that is a pre-existing query_v3 engine issue, not a regression from the type-token fold. JVM `instance?` of the tokens against constructed and `parse-query` AST nodes is true for the matching type and false for the others.
